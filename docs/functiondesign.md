## 1. 概要

### 1.1 システム概要

本AIは、6x6オセロにおいて、標準盤面および `BLOCK` を含む変形盤面で対戦する大会提出用プレイヤーである。

本AIの目的は、単に通常オセロで強い手を選ぶことではなく、`BLOCK` によって盤面構造が変化した場合でも、合法手生成・探索・評価を破綻させず、安定して勝率を上げることである。

特に、以下を重視する。

* `BLOCK` を含む盤面の正確な内部表現
* 不正手を返さない合法手生成
* 持ち時間内に必ず手を返す時間制御
* αβ探索による読みの強化
* 変形盤面に対応した評価関数
* 終盤完全読みによる勝敗確定精度の向上

### 1.2 実装方針

| 項目       | 内容                    |
| -------- | --------------------- |
| 言語       | Java 17               |
| プレイヤークラス | `p26xdd.OurPlayer`    |
| 継承元      | `ap26.Player`         |
| 内部盤面     | 独自 `MyBoard`          |
| 探索方式     | Negamax + αβ枝刈り       |
| 探索制御     | 反復深化 + 時間制御           |
| 評価方式     | 複合評価関数                |
| 対応盤面     | 標準盤面 / `BLOCK` 付き変形盤面 |
| 最優先要件    | 合法手を時間内に返すこと          |

### 1.3 用語定義

| 用語      | 説明                             |
| ------- | ------------------------------ |
| `BLOCK` | 石を置けず、反転判定も通過できない通行不可マス        |
| 合法手     | 現在の手番プレイヤーがルール上置ける手            |
| パス      | 合法手が存在しない場合に返す手                |
| 終局      | 双方が合法手を持たない状態                  |
| αβ探索    | Minimax探索の枝刈り付き探索              |
| 反復深化    | 深さ1から順に探索し、時間内で読める最大深さまで探索する方式 |
| 機動力     | 自分または相手の合法手数                   |
| 安定石     | 今後反転されにくい石                     |
| 疑似角     | `BLOCK` や盤外により角に近い安定性を持つマス     |
| 危険マス    | 次に相手へ角・疑似角を与えやすいマス             |

知能処理演習2の内容を踏まえ、既存設計に以下の機能を追加する。

## 3. 基本機能仕様

### 3.1 プレイヤー初期化機能

| 項目    | 内容                              |
| ----- | ------------------------------- |
| 機能ID  | FUNC-001                        |
| 機能名   | プレイヤー初期化                        |
| 対象クラス | `OurPlayer`                     |
| メソッド  | `public OurPlayer(Color color)` |
| 複雑度   | 低                               |

**処理概要:**

プレイヤーの手番色を受け取り、自分の色・相手の色・探索設定・時間管理用変数を初期化する。

**処理フロー:**

1. 引数 `color` を自分の色として保存する
2. 相手色を計算する
3. 探索深さの初期値を設定する
4. 総持ち時間管理用の変数を初期化する
5. 内部盤面を未設定状態にする

**注意点:**

`static` フィールドに対局状態を持たせない。
複数対局が並列実行されても、外部副作用を出さない設計にする。

### 3.2 初期盤面設定機能

| 項目    | 内容                                  |
| ----- | ----------------------------------- |
| 機能ID  | FUNC-002                            |
| 機能名   | 初期盤面設定                              |
| 対象クラス | `OurPlayer`, `MyBoard`              |
| メソッド  | `public void setBoard(Board board)` |
| 複雑度   | 中                                   |

**処理概要:**

大会システムから渡される初期盤面を内部盤面へコピーする。標準盤面だけでなく、`BLOCK` を含む変形盤面もそのまま保持する。

**処理フロー:**

1. `Board` から全36マスを読み取る
2. 各マスの状態を内部配列へコピーする
3. `BLOCK` マスを記録する
4. 初期石配置を記録する
5. 盤面解析情報を更新する

**内部データ例:**

```java
Color[] cells = new Color[36];
boolean[] isBlock = new boolean[36];
```

**注意点:**

`Board` の具象クラスを仮定しない。
必ず `ap26.Board` インタフェース経由で盤面情報を取得する。

### 3.3 着手選択機能

| 項目    | 内容                               |
| ----- | -------------------------------- |
| 機能ID  | FUNC-003                         |
| 機能名   | 着手選択                             |
| 対象クラス | `OurPlayer`                      |
| メソッド  | `public Move think(Board board)` |
| 複雑度   | 最高                               |

**処理概要:**

現在の盤面を受け取り、合法手の中から最善手を選択して返す。

**処理フロー:**

1. `Board` から内部盤面へ全マスコピーする
2. 自分の合法手一覧を生成する
3. 合法手がない場合はパスを返す
4. 探索開始時刻を記録する
5. 反復深化探索を開始する
6. 各深さで最善手を更新する
7. 時間が危なくなった場合は探索を打ち切る
8. 最後に完了した深さの最善手を返す

**例外時のフォールバック:**

探索中に時間切れが近づいた場合でも、必ず合法手リストの先頭または直前の最善手を返す。

**注意点:**

この機能が最も重要である。
評価関数が優れていても、ここで不正手・時間切れ・例外が発生すれば即敗北になる。

## 4. 探索機能仕様

### 4.1 Negamax + αβ探索

| 項目    | 内容       |
| ----- | -------- |
| 機能ID  | FUNC-004 |
| 機能名   | αβ探索     |
| 対象クラス | `Search` |
| 複雑度   | 高        |

**処理概要:**

現在局面から指定深さまで探索し、自分にとって最も評価値が高い手を選ぶ。

**探索方式:**

```text
Negamax(board, depth, alpha, beta, color)
```

**処理フロー:**

1. 終局または深さ0なら評価関数を返す
2. 合法手一覧を生成する
3. 合法手がなければパス局面として相手番へ進める
4. 合法手を手順並び替えする
5. 各手を適用した子局面を探索する
6. 最大評価値を更新する
7. `alpha >= beta` なら枝刈りする
8. 評価値を返す

**評価視点:**

評価値は常に現在手番側から見た値として扱う。
実装を単純にするため、Negamax形式で符号反転を利用する。

---

### 4.2 反復深化探索

| 項目    | 内容                    |
| ----- | --------------------- |
| 機能ID  | FUNC-005              |
| 機能名   | 反復深化                  |
| 対象クラス | `Search`, `OurPlayer` |
| 複雑度   | 高                     |

**処理概要:**

探索深さを1から順に増やし、時間内に完了した最大深さの結果を採用する。

**処理フロー:**

1. 深さ1から探索を開始する
2. 探索が完了したら最善手を保存する
3. 次の深さへ進む
4. 時間制限に近づいたら探索を中断する
5. 最後に完了した深さの最善手を返す

**採用理由:**

固定深さ探索では、局面によって探索時間が大きく変動する。
反復深化を使うことで、どの局面でも最低限の手を確保しながら、時間の許す範囲で深く読める。

---

### 4.3 手順並び替え

| 項目    | 内容             |
| ----- | -------------- |
| 機能ID  | FUNC-006       |
| 機能名   | 手順並び替え         |
| 対象クラス | `MoveOrdering` |
| 複雑度   | 高              |

**処理概要:**

αβ探索の枝刈り効率を上げるため、良さそうな手から優先的に探索する。

**優先順位:**

| 優先度 | 手の種類         | 理由                 |
| --- | ------------ | ------------------ |
| 1   | 終局で勝てる手      | 勝敗が確定するため          |
| 2   | 角を取る手        | 安定しやすいため           |
| 3   | 疑似角を取る手      | 変形盤面で強い可能性があるため    |
| 4   | 相手の合法手数を減らす手 | 機動力を奪えるため          |
| 5   | 安定石を増やす手     | 終盤で有利になりやすいため      |
| 6   | 石を取りすぎない手    | 序盤の過剰取得を避けるため      |
| 7   | 危険マス         | 相手に角を渡す可能性があるため後回し |

**注意点:**

手順並び替えは評価値そのものではなく、探索効率を上げるための処理である。
ただし、浅い探索では事実上の選好にもなるため、危険マス判定は雑に実装しない。

### 4.4 トランスポジションテーブル

| 項目    | 内容                                      |
| ----- | --------------------------------------- |
| 機能ID  | FUNC-017                                |
| 機能名   | トランスポジションテーブル                       |
| 対象クラス | `Search`, `TranspositionTable`, `TTEntry` |
| 複雑度   | 高                                       |
| 優先度   | 高                                       |

**処理概要:**

探索済み局面の評価値をハッシュテーブルに保存し、同じ局面が再び現れたときに再利用する。
反復深化探索では、浅い深さで探索した局面が深い探索中にも現れやすいため、特に効果が大きい。

**利用例:**

```text
深さ1で探索した局面の評価値を保存する
深さ2の探索中に同じ局面が現れたら再計算せず再利用する
異なる手順から同じ盤面に到達した場合も同一局面として扱う
```

**エントリ構造:**

```java
record TTEntry(
    long hash,
    int depth,
    int score,
    EntryType type,
    Move bestMove
) {}

enum EntryType {
    EXACT,       // α < score < β だった確定値
    LOWER_BOUND, // score >= β でカットされた下限値
    UPPER_BOUND  // score <= α だった上限値
}
```

**探索時の利用方針:**

1. 探索開始時に局面ハッシュを計算する
2. 置換表に同じハッシュがあるか確認する
3. 保存済み深さが現在要求深さ以上なら再利用候補にする
4. `EntryType` に応じて `alpha` / `beta` / 確定値を更新する
5. カットできる場合は子ノードを展開せず評価値を返す
6. 探索終了時に評価値・深さ・種別・最善手を保存する

**保存種別の意味:**

| 種別 | 意味 | 利用方法 |
| --- | --- | --- |
| `EXACT` | 真の評価値が確定している | そのまま返せる |
| `LOWER_BOUND` | 実際の評価値は保存値以上 | `alpha` 更新に使う |
| `UPPER_BOUND` | 実際の評価値は保存値以下 | `beta` 更新に使う |

**対称性の扱い:**

標準盤面では、回転・反転で一致する局面を同一エントリとして扱える。
ただし、`BLOCK` を含む変形盤面では対称性が崩れるため、以下の条件分岐が必要である。

```java
long key;
if (board.hasBlock()) {
    key = board.zobristHash();          // 変形盤面はそのまま
} else {
    key = board.canonicalSymmetryHash(); // 標準盤面のみ対称性を正規化
}
```

**注意点:**

ハッシュだけで完全一致とみなすと衝突リスクがある。
提出規模では実害が小さい可能性はあるが、可能なら `hash` と盤面情報の軽い検証を併用する。

### 4.5 キラーヒューリスティック

| 項目    | 内容                          |
| ----- | --------------------------- |
| 機能ID  | FUNC-018                    |
| 機能名   | キラーヒューリスティック              |
| 対象クラス | `MoveOrdering`, `KillerMoveTable` |
| 複雑度   | 中                           |
| 優先度   | 最高                          |

**処理概要:**

ある深さで β カットを起こした手を「キラー手」として保存し、同じ深さの別ノードでも優先的に探索する。
実装量が少なく、手順並び替えにそのまま追加できるため、最初に入れる価値が高い。

**データ構造:**

```java
Move[][] killerMoves = new Move[MAX_DEPTH][2];
```

**保存処理:**

```java
void storeKiller(int depth, Move move) {
    if (!move.equals(killerMoves[depth][0])) {
        killerMoves[depth][1] = killerMoves[depth][0];
        killerMoves[depth][0] = move;
    }
}
```

**手順並び替えへの追加位置:**

| 優先順位 | 手の種類 |
| ---: | --- |
| 1 | 終局で勝てる手 |
| 2 | 角を取る手 |
| 3 | 疑似角を取る手 |
| 4 | キラー手 |
| 5 | 相手の合法手数を減らす手 |
| 6 | 安定石を増やす手 |
| 7 | 石を取りすぎない手 |
| 8 | 危険マス |

**注意点:**

キラー手は「その局面で常に良い手」ではなく、「同じ深さでカットを起こしやすい手」である。
評価関数の代わりではなく、探索順序を改善するための補助として扱う。

### 4.6 PVS（Principal Variation Search）

| 項目    | 内容                |
| ----- | ----------------- |
| 機能ID  | FUNC-019          |
| 機能名   | PVS探索             |
| 対象クラス | `Search`          |
| 複雑度   | 高                 |
| 優先度   | 中                 |

**処理概要:**

PVSは、Negamax + αβ探索を前提にした探索高速化である。
最善手候補だけ通常のαβ探索を行い、2手目以降はまず狭い探索窓で「現在の `alpha` を超える可能性があるか」だけを確認する。

**導入条件:**

PVSは Move Ordering が弱い状態で入れるべきではない。
最善手候補を先頭に置けないと Null Window Search が失敗し、再探索が増えて逆に遅くなる。

**探索骨格:**

```java
for (int i = 0; i < moves.size(); i++) {
    Move move = moves.get(i);
    MyBoard child = board.apply(move);

    int score;
    if (i == 0) {
        // 最善手候補は通常の αβ 探索
        score = -negamax(child, depth - 1, -beta, -alpha);
    } else {
        // 2手目以降はまず null-window で可能性だけ確認
        score = -negamax(child, depth - 1, -alpha - 1, -alpha);

        // alpha を改善する可能性があるなら通常探索でやり直す
        if (score > alpha && score < beta) {
            score = -negamax(child, depth - 1, -beta, -alpha);
        }
    }

    if (score > alpha) {
        alpha = score;
        bestMove = move;
    }

    if (alpha >= beta) {
        break;
    }
}
```

**導入順序:**

```text
合法手生成
→ 固定深さ Negamax + αβ
→ 反復深化
→ Move Ordering
→ キラーヒューリスティック
→ トランスポジションテーブル
→ PVS
```

**注意点:**

PVSは探索の正しさを壊しやすい。
まず通常の Negamax + αβ で探索結果を固定し、同じ局面でPVS版と評価値・最善手が一致するかをテストしてから差し替える。

### 5.4 LOGISTELLO型パターン評価

| 項目    | 内容                              |
| ----- | ------------------------------- |
| 機能ID  | FUNC-020                         |
| 機能名   | パターン特徴に基づく評価関数                 |
| 対象クラス | `PatternEvaluator`, `WeightTrainer` |
| 複雑度   | 最高                              |
| 優先度   | 低                               |

**処理概要:**

盤面を辺・角・斜め・縦横などのパターンに分解し、各パターンに現れる石配置を特徴量として評価する。
LOGISTELLO型の評価関数では、特徴量の線形和で局面を評価し、自己対戦やプレイアウト結果から重みを学習する。

**評価式:**

```text
f(p) = Σ wi * fi(p)
```

| 記号 | 意味 |
| --- | --- |
| `p` | 局面 |
| `fi(p)` | 局面 `p` における特徴量 |
| `wi` | 特徴量 `fi` の重み |
| `f(p)` | 局面評価値 |

**パターン例:**

| パターン | 内容 |
| --- | --- |
| `diag` | 斜めライン |
| `hor` | 横ライン |
| `vert` | 縦ライン |
| `edge` | 辺 |
| `corner` | 角周辺 |
| `edge+2X` | 辺と危険マスを含む形 |
| `3x3-corner` | 角周辺3x3領域 |

**6x6実装での扱い:**

本AIでは、いきなり100万パラメータ級の評価関数を作るべきではない。
大会直前の実装では、既存の角評価・疑似角評価・危険マス評価を優先する。
パターン評価は、以下の条件を満たした後にローカル実験として導入する。

1. 合法手生成が完全に正しい
2. αβ探索と時間制御が安定している
3. 自己対戦を大量実行できる
4. 探索ログを Tablesaw で集計できる
5. 評価重みを差し替えて勝率比較できる

**注意点:**

パターン評価は強力だが、学習データが弱いと評価関数も弱くなる。
学習基盤なしで形だけ実装しても、固定重み評価より弱くなる可能性が高い。


## 6. 変形盤面対応仕様

### 6.1 `BLOCK` 対応

| 項目    | 内容                         |
| ----- | -------------------------- |
| 機能ID  | FUNC-010                   |
| 機能名   | `BLOCK` 盤面対応               |
| 対象クラス | `MyBoard`, `BoardAnalyzer` |
| 複雑度   | 最高                         |

**処理概要:**

`BLOCK` を石でも空きマスでもない障害物として扱う。
合法手生成・反転判定・評価関数のすべてで `BLOCK` を考慮する。

**仕様:**

* `BLOCK` には置けない
* `BLOCK` は反転しない
* `BLOCK` をまたいで相手石を挟めない
* `BLOCK` は盤面端と似た性質を持つ場合がある
* `BLOCK` の位置によって角・辺の価値を再計算する

**反転判定の停止条件:**

```text
盤外に出た
空きマスに到達した
BLOCK に到達した
自石に到達した
```

このうち、相手石列の先に自石がある場合のみ反転可能とする。

---

### 6.2 疑似角評価

| 項目    | 内容                        |
| ----- | ------------------------- |
| 機能ID  | FUNC-011                  |
| 機能名   | 疑似角評価                     |
| 対象クラス | `BoardAnalyzer`, `MyEval` |
| 複雑度   | 高                         |

**処理概要:**

盤外または `BLOCK` によって複数方向が塞がれているマスを、通常より安定しやすいマスとして評価する。

**判定例:**

| 条件                  | 評価       |
| ------------------- | -------- |
| 通常角                 | 最大評価     |
| 盤外2方向に接する           | 角として評価   |
| 盤外1方向 + `BLOCK` 1方向 | 疑似角として評価 |
| `BLOCK` 2方向に接する     | 疑似角として評価 |
| 片側のみ `BLOCK`        | 軽く加点     |

**注意点:**

疑似角は通常角と同じ価値にしない。
`BLOCK` に接していても、別方向から反転される可能性があるため、過大評価は危険である。

---

### 6.3 安定石評価

| 項目    | 内容                        |
| ----- | ------------------------- |
| 機能ID  | FUNC-012                  |
| 機能名   | 安定石評価                     |
| 対象クラス | `BoardAnalyzer`, `MyEval` |
| 複雑度   | 高                         |

**処理概要:**

盤外、角、`BLOCK`、疑似角から連続している自石を安定石候補として評価する。

**評価対象:**

* 角から辺に沿って連続する自石
* `BLOCK` によって片側が遮断された辺上の自石
* 疑似角から連続する自石
* 終盤で反転可能性が低い自石

**簡易実装方針:**

1. 角または疑似角を起点にする
2. 辺方向へ自石が連続しているか確認する
3. 連続している石に加点する
4. 相手石または空きマスで停止する

**注意点:**

完全な安定石判定は実装コストが高い。
初期実装では「辺上の安定候補」に限定してよい。

### 6.4 ビットボード試作方針

| 項目    | 内容                          |
| ----- | --------------------------- |
| 機能ID  | FUNC-021                    |
| 機能名   | ビットボード盤面表現                 |
| 対象クラス | `BitBoard`, `BitBoardBoard` |
| 複雑度   | 最高                          |
| 優先度   | 中期                          |

**処理概要:**

6x6盤面は36マスであるため、`long` の下位36ビットに収められる。
自石・相手石・`BLOCK` をそれぞれビット集合として持つことで、合法手生成や反転判定をシフト演算とビット演算で高速化できる。

**表現例:**

```java
long blackBits; // 黒石の位置
long whiteBits; // 白石の位置
long blockBits; // BLOCK の位置
```

**メリット:**

* 合法手生成を方向ごとのシフトとAND/ORで処理できる
* 反転対象をビット集合として一括計算できる
* 石数計算に `Long.bitCount()` を使える
* 最下位ビット抽出に `x & -x` を使える
* ハッシュ計算や盤面コピーが軽くなる

**基本操作例:**

```java
long lsb = x & -x;             // 最下位の1ビットを抽出
int count = Long.bitCount(x);  // 立っているビット数を数える
x |= (1L << index);            // index番目を1にする
x &= ~(1L << index);           // index番目を0にする
```

**導入方針:**

現在の `MyBoard` を直接置き換えるのは危険である。
まず `BitBoardBoard` を別クラスとして作成し、同じ局面に対して以下が一致するかをテストする。

| 比較項目 | 期待結果 |
| --- | --- |
| 合法手一覧 | `MyBoard` と完全一致 |
| 着手後盤面 | `MyBoard` と完全一致 |
| 反転石数 | `MyBoard` と完全一致 |
| 終局判定 | `MyBoard` と完全一致 |
| 評価値 | `MyEval` と完全一致または説明可能な差分 |

**注意点:**

ビットボードは速いが、バグると合法手生成と反転処理が同時に壊れる。
最初から採用するのではなく、配列版が正しく動いた後に速度比較して乗り換える。

| 複雑度   | 中                              |

**処理概要:**

Tablesaw の Plotly 連携を使い、探索を繰り返した結果をグラフで確認する。
表だけでは見つけにくい「深さを上げると遅くなる局面」「変形盤面だけ評価が崩れる局面」「特定重みで勝率が落ちる局面」を視覚的に確認する。

**メソッド案:**

```java
void plotWinRateByModel(Table summary)
void plotElapsedMillisByDepth(Table table)
void plotScoreTimeline(Table table, String gameId)
void plotEvalBreakdown(Table table, String gameId, int turn)
```

**グラフ案:**

| グラフ | 横軸 | 縦軸 | 目的 |
| --- | --- | --- | --- |
| モデル別勝率 | 評価モデル名 | 勝率 | 重みセットを比較する |
| 深さ別探索時間 | 探索深さ | 平均探索時間 | 時間切れリスクを見る |
| 手数ごとの評価推移 | 手数 | 探索評価値 | 形勢判断の急変を見る |
| 評価内訳棒グラフ | 評価項目 | 評価値 | どの要素が手を選ばせたか見る |
| 盤面種別別ノード数 | 盤面種別 | ノード数 | 変形盤面で探索が重くなるか見る |

**注意点:**

グラフ出力はローカルPCでの分析用とする。

### 9.3 実装リスク

| リスク               | 影響      | 対策                  |
| ----------------- | ------- | ------------------- |
| `BLOCK` をまたいで反転する | 不正手・誤探索 | 方向探索の停止条件を明確化する     |
| 内部盤面が実盤面とズレる      | 不正手     | 毎回 `Board` から全コピーする |
| 探索が時間切れする         | 即負け     | 反復深化と安全マージンを入れる     |
| 評価関数が通常盤面に偏る      | 変形盤面で弱い | 疑似角・安定石評価を入れる       |
| 序盤で石を取りすぎる        | 中盤以降で不利 | 序盤の石差重みを下げる         |
| 終盤で勝ちを逃す          | 勝率低下    | 空きマスが少ない場合は完全読みに寄せる |
| デバッグ用Tablesawが提出物に混入する | 提出サイズ増加・実行環境不一致 | ローカル検証用パッケージに分離し、提出zipから除外する |
| 置換表の境界種別を保存しない | 誤った評価値再利用 | `EXACT` / `LOWER_BOUND` / `UPPER_BOUND` を必ず保存する |
| PVSを早く入れすぎる | 再探索増加・バグ混入 | 通常αβと結果比較してから導入する |
| 対称性正規化を変形盤面に使う | 別局面を同一扱いする | `BLOCK` ありでは対称性正規化を無効化する |
| ビットボード移行で合法手がズレる | 不正手・評価崩壊 | 配列版 `MyBoard` と全局面比較してから採用する |
| パターン評価を学習なしで入れる | 固定評価より弱くなる | 自己対戦ログと勝率比較が可能になってから使う |

## 10. 補足: この設計で最も重要な点

このAI設計で一番重要なのは、**強い評価関数を最初から作ることではない**。

優先順位を間違えると失敗する。

```text
誤った優先順位:
評価関数を凝る
→ 探索を後回し
→ 時間制御が雑
→ 不正手・時間切れで負ける
```

正しい優先順位はこれ。

```text
合法手を必ず返す
→ BLOCK対応を正しくする
→ 時間内に探索する
→ αβ探索を安定させる
→ 評価関数を変形盤面向けに強化する
```

変形盤面に強いAIを作るなら、固定マス重み表に依存する設計は捨てるべきです。
`BLOCK` によって、角・辺・危険マスの意味が変わるため、盤面ごとに価値を再計算する設計が必要です。
