# プログラミング応用杯のルール

プレイヤ（参加プログラム）は、次のルールに従うこと。ここで `dd` は、チームを表す 2 桁の整数である。

`dd < 10` の場合は、`01` のように 0 埋めすること。

## ルール

1. **作成者**

   チームメンバが作成したコードにより正々堂々と戦うこと。

2. **プログラミング言語**

   Java 17 のみで動作すること。

3. **継承**

   プレイヤは、抽象クラス `ap26.Player` を継承すること。

4. **名称**

   プレイヤのパッケージ・クラス・プレイヤ名を次のようにする。プレイヤ名は半角英数字（ASCII）4 文字とし、他のチームと重複しないように調整すること（勝敗表の整形上、日本語や全角文字は使用不可）。重複が判明した場合は教員の調整に従うこと。

   - パッケージ名: `p26xdd`（例: `p26x01`, `p26x42`）
   - クラス名: `OurPlayer`
   - プレイヤ名: 半角英数字 4 文字（例: `26AB`, `T042`, `0X1Z`）

5. **必須メソッド**

   プレイヤは、次のメソッドを実装すること。

   1. `public OurPlayer(Color color)`

      コンストラクタである。`color` は手番順を表し、`BLACK` は先手、`WHITE` は後手である。

   2. `public Move think(Board board)`

      盤面 `Board` を受け取り、次の手 `Move` を返すメソッドである。ここで `Move` の完全修飾名は `ap26.Move` である。`Board` はインタフェース `ap26.Board` に従うことを仮定し、特定の実装を想定してはならない。探索時に内部で特定の実装を用いてもよい。

   3. `public void setBoard(Board board)`

      対戦前に初期の盤面を受け取るために呼ばれる関数である。

6. **対戦形式**

   総当たり戦。各プレイヤーのペア（自分対自分を除く）について、複数の盤面で先手・後手の両方を対戦する。

   - 盤面数: 3 盤面（標準盤 1 枚 + 変形盤 2 枚）
   - 各盤面で先手・後手を入れ替えて 2 局 ⇒ 1 ペアあたり計 6 局
   - `N` プレイヤー参加なら総ゲーム数 = `N × (N − 1) × 6`

7. **特殊ルール（変形盤）**

   標準オセロに加え、特定マスを通行不可（`BLOCK`）にした変形盤面を含む。

   - `BLOCK` の候補位置: `a1`, `b1`, `c1`, `d1`, `e1`, `f1`, `a2`, `a3`, `a4`, `a5`, `a6`（11 マス）
   - 配置個数: 1～3 個（一様乱数）
   - 配置方法: 候補から無作為抽選
   - 配置タイミング: 対戦当日に生成。生成方式は事前公開、具体的な盤面は当日まで非公開

   学生は同じ生成方式で乱数を回し、変形盤に強いアルゴリズムを準備するとよい。

8. **実行環境**

   `cse.cs.nitech.ac.jp` を用いる。各プレイヤーは独立した JVM プロセスで実行され、Socket 通信を介して対局システムと連携する。

9. **持ち時間**

   1 ゲームあたり 60 秒。各ゲームにおいて自分の手番で用いる実時間の合計が 60 秒を超えた時点で、そのゲームは負けとなる。ゲームが始まるたびに持ち時間はリセットされる（ゲームをまたいで持ち越せない）。

10. **勝敗**

    終局時の石の数が多いプレイヤーを勝ちとする。次の場合は、当該ゲームで即時負けとなる。

    1. 規定の対戦環境において正常に動作しない場合
    2. オセロのルールに違反した場合（合法でない手の返却）
    3. 持ち時間を超過した場合
    4. 不正が発覚した場合

    即時負けの扱いはゲーム単位（次のゲームには影響しない）。同一プレイヤーが連続で失格しても、各ゲームを独立に判定する。

11. **引き分け**

    双方とも合法手がなくなった状態で、石数が同数の場合を引き分けとする。

12. **順位**

    次の優先度で順序付けする。

    1. 勝ち数の降順
    2. 勝ち点の降順
    3. 直接対戦の勝率の降順
    4. 処理時間の昇順
    5. 上記すべて同点の場合は共同優勝（再対戦は行わない）

13. **勝ち点**

    各ゲームごとに以下の計算で勝ち点を加算する。

    1. 勝ち: `10 + min(自分の石数 − 相手の石数, 10)`（最小 10、最大 20）
    2. 引き分け: 5
    3. 負け: 0
    4. 即時負け（失格）: 相手に最大点（20）を与える。自身は 0

    例: 19-17 の僅差勝ちは `10 + min(2, 10) = 12` 点。35-1 の圧勝なら `10 + min(34, 10) = 20` 点。この設計により、勝つこと自体に 10 点の価値を置き、圧勝バイアスを抑制している。

14. **禁止事項**

    1. 他のプログラムや外部サービスを利用してはならない。
    2. 通信してはならない。プロセス間通信、ファイルへの書き込み、ネットワークアクセスを含む。
    3. `ap26` パッケージ内のプログラムを一切変更してはならない。
    4. 過剰な標準出力・標準エラー出力を行ってはならない（目安: 1 ゲームあたり 100 行以内）。

15. **ファイル I/O とリソース**

    学習済みモデルや設定値などのファイルを利用する場合は、次の規約に従うこと。

    1. リソース配置: パッケージ内の `p26xdd/resources/` ディレクトリに配置する。提出 zip にこのディレクトリを含めること。
    2. サイズ上限: `resources/` 配下の合計サイズは 10 MB を上限とする。
    3. 読み込み方法: 必ず `ap26.ResourceLoader` 経由で読み込むこと。

       ```java
       byte[] model = ResourceLoader.readAllBytes(getClass(), "model.bin");
       String csv = ResourceLoader.readString(getClass(), "weights.csv");

       try (InputStream is = ResourceLoader.open(getClass(), "model.bin")) {
           ...
       }
       ```

    4. 学生コードからの直接のファイル I/O は全面禁止する。具体的には `java.io.File*`、`java.io.FileInputStream`、`java.io.FileReader`、`java.nio.file.Files` 等のファイル系 API、および `getResourceAsStream`、`Class.getResource` の直接利用も禁止する。リソースアクセスは `ap26.ResourceLoader` の経路に限定する。
    5. ファイルへの書き込みは一切禁止する（`FileOutputStream`, `FileWriter`, `Files.write*`, `PrintWriter`, `ObjectOutputStream`, `FileChannel.write*` 等）。これは「ファイルを経由した通信（カンニング）」を構造的に排除するためである。書き込み手段を一切持たないため、`ResourceLoader` は読み込み専用 API のみを提供している。

    **注意:** 提出物に対し、上記禁止 API の利用を機械検査することがある。違反が検出された場合は失格とする。

16. **AI ツールの利用**

    LLM 等の AI ツールを用いてコードを生成・改善することは認める。ただし、提出コードについて各クラス・各メソッドの存在意義と動作を自分の言葉で説明できること。提出後に口頭試問を行うことがあり、説明できない場合は失格とする。

17. **提出物**

    Moodle の指定箇所に zip ファイルで提出する。

    - ファイル名: `p26xdd.zip`
    - 内容: パッケージ `p26xdd` 配下の全 Java ソース
    - `ap26` パッケージは含めないこと（共通実装のため）

18. **注意事項**

    同時に複数の対戦を並列実行する。プレイヤーは独立プロセスで動作するため、グローバル変数（static フィールド等）の影響は同一プレイヤー内に限定される。ただしファイル I/O 等で外部に副作用を出さないこと。
