# ゲームオセロAI 実装方針

## 前提

本プロジェクトでは、`ap26/` を大会側が提供する共通 API、`myplayer/` を現在の参考実装として扱う。大会提出時は `ap26/` を変更・同梱せず、自分たちのプレイヤー実装だけを指定パッケージ `p26xdd` に移して提出する。

対象ゲームは 6x6 オセロである。標準盤面に加えて、特定マスが `Color.BLOCK` となる変形盤面が当日使われるため、評価関数と探索は「角・辺が常に通常盤どおり強い」と決め打ちしすぎない方針にする。

## API と提出条件への対応

- プレイヤークラスは `ap26.Player` を継承し、提出用パッケージ `p26xdd` に `OurPlayer` として配置する。
- コンストラクタは `public OurPlayer(Color color)` を必ず用意する。
- `think(Board board)` は `ap26.Board` インタフェースだけに依存し、渡された `Board` の具象クラスを仮定しない。
- `setBoard(Board board)` では初期盤面を内部盤面へコピーする。標準盤だけでなく `BLOCK` を含む変形盤もそのまま保持する。
- `ap26/` 配下は大会共通実装なので変更しない。
- 直接のファイル I/O、通信、過剰な標準出力は行わない。デバッグ出力は提出前に削除する。
- 持ち時間は 1 ゲーム合計 60 秒なので、1 手ごとの探索時間を安全側に制限する。

## 現状実装の整理

`myplayer/MyBoard.java` は `ap26.Board` を実装した内部盤面で、`Color[]` に 36 マスを保持している。合法手生成、石の反転、パス、終局判定、色反転 `flipped()` を担当しており、`BLOCK` は `outflanked()` で探索線を止める障害物として扱われている。

`myplayer/MyEval.java` は黒視点の評価関数である。現在は終局時に `1_000_000 * score()` を返し、非終局時は固定のマス重み表で評価している。

`myplayer/MyPlayer.java` は固定深さの α-β 探索で着手を選ぶ。白番では盤面を `flipped()` して常に黒視点で探索し、ルートで見つけた最善手を `this.move` に保存して返す。

この構成は分かりやすく、提出実装の土台にしやすい。一方で、深さ固定、ランダムな手順並び替え、固定マス重みだけでは大会形式では不安が残るため、以下の順に強化する。

## 実装方針

### 1. 提出用クラスへ移植する

まず `myplayer` の実装を提出用パッケージへ移す。基本構成は次のようにする。

- `p26xdd.OurPlayer`: `ap26.Player` を継承する本体。
- `p26xdd.MyBoard`: 探索用の内部盤面。`Board` から全マスをコピーできるようにする。
- `p26xdd.MyEval`: 評価関数。

`RandomPlayer`・`MyGame`・`MyBoardFormatter` はローカル検証用であり、提出対象から外す。提出 zip には `p26xdd` パッケージ配下のプレイヤー実装のみを含める。

### 2. 内部盤面を大会盤面に確実に同期する

盤面の取り込みは次の2段階で管理する。全マスを毎回コピーするのは非効率なため、`setBoard` で全コピーを行い、`think` では変化したマスだけを差分更新する。

**`setBoard(Board board)` の役割（ゲーム開始時に1回）**

- 渡された `Board` の全 36 マスを内部盤面へコピーする。
- `BLOCK` の位置を記録する。`BLOCK` はゲームを通じて変化しないため、以後の `think` 呼び出しでは再記録しない。
- 持ち時間タイマーをリセットする。

**`think(Board board)` の役割（自分の手番ごと）**

毎回全マスをコピーせず、前回からの差分だけを内部盤面へ反映する。具体的な手順は次のとおり。

1. `board.getMove()` で相手の直前の着手を取得する。
2. その着手がパスであれば内部盤面の変更は不要。
3. 通常の着手であれば、置かれたマスと反転されたマスだけを内部盤面へ反映する（反転処理は既存の `MyBoard` の着手適用ロジックを流用できる）。
4. 探索を行い最善手を決定する。
5. 決定した手を自分の着手として内部盤面へ反映してから返す。これにより、次の `think` 呼び出し時には自分の前回手もすでに内部盤面に乗っている状態になる。

この方式では、1 手あたりの更新コストが「1 マス配置 + 数マスの反転」のみとなり、毎回 36 マスコピーに比べて大幅に削減できる。

**注意点:**

差分更新は `setBoard` で取り込んだ初期盤面が正しいことが前提である。`setBoard` の全コピーが誤っていると以後の更新がすべてずれるため、`setBoard` の実装は特に丁寧に検証する。デバッグ時は `board` の全マスと内部盤面を比較するアサーションを入れ、一致を確認してから差分更新に切り替えるとよい。

### 3. 時間制御付き反復深化にする

現在は `depthLimit = 2` の固定深さである。大会では 1 ゲーム合計 60 秒なので、残り時間を管理しながら反復深化を行う。

探索ループの管理は `Search` クラスが担当する。`OurPlayer` は `Search` を呼び出して最善手を受け取るだけとし、探索中断の判断・暫定最善手の保持はすべて `Search` 内で完結させる。

反復深化の流れは次のとおり。

- 深さ 1 から順に α-β 探索する。
- 各深さが完了した時点の最善手を `Search` 内の暫定最善手として保存する。
- 1 手の制限時間に近づいたら探索を打ち切り、最後に完了した深さの最善手を返す。
- 終盤で空きマスが少ない場合は深く読む。

**1 手あたりの制限時間の計算式:**

```
1手の制限時間 = 残り持ち時間 / 残り空きマス数 × 0.8
ただし、最小 0.1 秒、最大 2.0 秒にクランプする
```

さらに締切の 150ms 前に探索を打ち切り、暫定最善手を返す。持ち時間超過は即負けなので、常に暫定最善手を確保した状態で探索する。

### 4. 手順並び替えを強化する

現在の `order()` は `Collections.shuffle()` のみで、α-β の枝刈り効率が安定しない。次の優先順位で合法手を並び替える。

1. 終局で勝てる手。
2. 角を取る手。
3. `BLOCK` によって安定しやすい疑似角を取る手。
4. 相手の合法手数を減らす手。
5. 自分の安定石を増やす手。
6. 危険な X マス・C マスに相当する手は、角を取られる可能性が高い場合に後回し。

序盤で石を取りすぎることへの対策は、手順並び替えでは行わない。後述の評価関数で序盤の石差重みを負にすることで対応する。

手順並び替えは評価値そのものを変えなくても探索効率を大きく改善できるため、優先して実装する。

### 5. 評価関数を局面段階ごとに分ける

固定マス重みだけでは、序盤で石を増やしすぎる手や、変形盤で実質的に弱くなった角を過大評価する危険がある。評価関数は次の要素を組み合わせる。

**局面段階の定義（空きマス数による分類）:**

| 局面 | 条件          | 残り手数目安 |
| -- | ----------- | ------ |
| 序盤 | 空きマス ≥ 20   | 序盤12手  |
| 中盤 | 10 ≤ 空きマス < 20 | 中盤10手 |
| 終盤 | 空きマス < 10   | 終盤10手  |

6×6 盤面は初期空きマスが 32 であるため、この境界値を基準にする。

**各段階での重視項目:**

- 終局: `score()` を最優先する。勝ちは `+1,000,000 + 石差`、引き分けは `-10,000`、負けは `-1,000,000 + 石差` とする。引き分けに負の評価を与えるのは、勝ちを狙える局面で安易に引き分け手順へ流れることを防ぐためである。
- 序盤: 機動力（自分の合法手数と相手の合法手数の差）を重視する。石差の重みは負（-5 程度）にし、序盤から石を取りすぎて相手の合法手を増やす手を自然に抑制する。
- 中盤: 角、疑似角、安定石、相手の手数制限を重視する。
- 終盤: 実石差と確定勝敗を重視し、空きマスが 8 以下になったら完全読みへ移行する。

`BLOCK` あり盤面では、通常の角だけでなく、`BLOCK` によって片側が塞がれた辺の石も安定しやすい。固定表だけでなく、盤面上の `BLOCK` 位置から安定度を計算する方針にする。

**疑似角の判定:**

疑似角は横方向・縦方向のみを考慮する。斜め方向に `BLOCK` や盤外があっても安定性には寄与しないため、判定から除外する。具体的には次の条件でマスの安定度を分類する。

| 条件                     | 評価       |
| ---------------------- | -------- |
| 横方向・縦方向ともに盤外           | 通常角（最大評価）|
| 横方向が盤外、縦方向が `BLOCK`（またはその逆） | 疑似角（中評価）|
| `BLOCK` 2方向（横・縦）に接する    | 疑似角（中評価）|
| 片側のみ `BLOCK`           | 軽く加点     |

疑似角は通常角より低く評価する。`BLOCK` に接していても別方向から反転される可能性があるため、過大評価しない。

### 6. パスと終局を正しく扱う

合法手がない場合は必ず `Move.ofPass(getColor())` を返す。`findLegalMoves()` はパスを含む設計なので、探索中も「合法手なしならパスして相手番へ進む」状態を正しく読む。

双方が合法手なしになったら終局である。終局評価では石数差を大きく評価し、勝てる終局手順が見えた場合は中間評価より優先する。

### 7. 変形盤面を重点的に検証する

大会では標準盤 1 枚と変形盤 2 枚で対戦する。変形盤は当日まで不明だが、候補位置と生成方法は分かっているため、ローカルで `BLOCK` を 1 から 3 個置いた盤面を複数作って検証する。

検証する内容は次の通り。

- `BLOCK` を挟んだ方向で石を反転しないこと。
- `BLOCK` マスを合法手として返さないこと。
- `setBoard` で保持した `BLOCK` が `think` 呼び出しのたびに消えないこと。
- パスが必要な局面で不正手を返さないこと。
- 標準盤と変形盤の両方で 60 秒以内に終局すること。

### 8. ローカル対戦で強さと安全性を見る

`myplayer/MyGame.java` はローカル検証用の簡易対戦ドライバとして使える。提出対象ではないが、検証には積極的に利用する。まずは `RandomPlayer` に安定して勝てることを確認し、その後、自分の AI 同士で深さや評価重みを変えて対戦させる。

見るべき指標は勝率だけでなく、反則手の有無、平均思考時間、終盤での取りこぼし、変形盤での不自然な着手である。

## 優先順位

1. 提出条件を満たす `p26xdd.OurPlayer` を作る。
2. `setBoard` で全 36 マスを一度コピーし `BLOCK` を記録する。同時にタイマーをリセットする。
3. `think` では `board.getMove()` で差分だけを内部盤面へ反映する。自分の手も探索後に内部盤面へ反映してから返す。
4. 合法手なし、パス、終局、不正手回避を固める。
5. 固定深さ α-β を反復深化 + 時間制御へ変更する。探索ループは `Search` に集約する。
6. 手順並び替えを導入する。
7. 評価関数を機動力、角、疑似角、安定石、終盤石差の複合評価へ拡張する。
8. 標準盤と複数の変形盤でローカル対戦を繰り返し、重みを調整する。

最重要は「強い手を返すこと」より先に「必ず合法手を時間内に返すこと」である。即時負けは勝ち点 0 になるため、探索を欲張りすぎず、常に暫定最善手を持ちながら安全に返す実装にする。
